# Техническое Задание (Версия 2.0)
## на разработку программного комплекса "Терминал бронирования Motel"

---

### 1. Общие сведения

#### 1.1. Назначение и цели создания системы
**Назначение:** Разработка программного комплекса (далее — "Система"), предназначенного для установки на стационарные терминалы (планшеты) с целью полной автоматизации процессов бронирования, оплаты и управления услугами в объектах размещения (отели, хостелы, мотели).

**Цели:**
- **Автоматизация:** Исключить или минимизировать участие персонала в стандартных операциях заселения и оплаты.
- **Скорость:** Сократить время, затрачиваемое гостем и персоналом на процесс оформления, до минимума.
- **Интеграция:** Обеспечить бесшовную и надежную интеграцию с существующим и будущим кассовым и платежным оборудованием.
- **Гибкость:** Предоставить администраторам мощный инструмент для гибкой настройки логики работы терминала, цен, услуг и внешнего вида.
- **Надежность:** Обеспечить стабильную работу Системы в режиме 24/7 с минимальным временем простоя.

#### 1.2. Целевая аудитория
- **Администраторы/Менеджеры:** Полная настройка Системы, управление контентом и оборудованием, просмотр расширенной отчетности.
- **Сотрудники ресепшн:** Использование терминала для оформления нестандартных операций, помощь гостям.
- **Гости:** Основные пользователи, осуществляющие самостоятельное бронирование и оплату.

### 2. Требования к системе

#### 2.1. Функциональные требования (Functional Requirements)

##### 2.1.1. Модуль аутентификации и доступа
- **FR-1 (Экран блокировки):**
  - **FR-1.1:** При запуске и после периода бездействия Система должна отображать полноэкранный экран блокировки.
  - **FR-1.2:** На экране должны отображаться анимированные фоновые изображения в режиме слайд-шоу, загружаемые с Бэкенда.
  - **FR-1.3:** Поверх фона должны отображаться крупные, легко читаемые цифровые часы и текущая дата в формате "День недели, число Месяц" (на русском языке).
  - **FR-1.4:** Разблокировка должна осуществляться интуитивным жестом "slide-to-unlock". После разблокировки должен открываться основной экран модуля бронирования.
- **FR-2 (Автоматическая блокировка):**
  - **FR-2.1:** Система должна непрерывно отслеживать бездействие пользователя (отсутствие касаний экрана) в модуле бронирования.
  - **FR-2.2:** При бездействии в течение 90 секунд, Система должна отображать модальное окно "Вы еще здесь?" с единственной кнопкой "Да". Нажатие на кнопку сбрасывает таймер бездействия.
  - **FR-2.3:** Если реакция на модальное окно не последовала в течение 60 секунд, оно должно автоматически закрыться, и Система должна перейти в режим блокировки (FR-1).
- **FR-3 (Доступ для администратора):**
  - **FR-3.1:** Должен быть реализован неявный механизм доступа к экрану аутентификации администратора: 5-кратное быстрое нажатие на виджет часов на экране блокировки.
  - **FR-3.2:** Экран аутентификации должен содержать поля "Логин", "Пароль" и экранную клавиатуру для ввода. При попытке входа должна отображаться индикация загрузки. В случае ошибки — выводиться четкое сообщение (например, "Неверный логин или пароль").
  - **FR-3.3:** После успешной аутентификации должен осуществляться переход в главный раздел модуля администрирования.

##### 2.1.2. Модуль бронирования
- **FR-4 (Мастер бронирования):**
  - **FR-4.1:** Весь процесс бронирования должен быть реализован в виде пошагового "мастера" (Stepper).
  - **FR-4.2:** Слева от основной области должна постоянно отображаться боковая панель (`Sidebar`), наглядно показывающая все этапы, подсвечивая текущий и отмечая пройденные.
  - **FR-4.3:** На каждом шаге должны быть доступны кнопки "Назад" (возврат к предыдущему шагу с сохранением данных) и "Отмена" (полный сброс процесса и возврат на экран блокировки). Кнопка "Продолжить" должна быть неактивна до тех пор, пока не выполнены все обязательные действия на текущем шаге.
- **FR-5 (Шаги мастера бронирования):**
  1.  **Выбор корпуса:** Отображение списка корпусов с иконками и кратким описанием. Выбранный вариант должен подсвечиваться.
  2.  **Выбор типа номера:** Список типов номеров (4-х, 6-ти, 8-ми местные) с иконками.
  3.  **Выбор комнаты и места:** Двухэтапный выбор. Сначала отображается список номеров комнат, доступных для выбранного типа. После выбора комнаты список меняется на перечень доступных в ней койко-мест.
  4.  **Ввод данных гостя:** Форма с полями "Фамилия", "Имя", "Отчество". Поля "Фамилия" и "Имя" обязательны для заполнения. Для ввода используется кастомная экранная клавиатура.
  5.  **Выбор категории операции:** Выбор из списка: "Проживание", "Услуги", "Штраф за нарушение правил", "Штраф за порчу имущества". От выбора на этом шаге зависит логика последующих шагов.
  6.  **Выбор периода:** Интерактивный календарь для выбора дат заезда и выезда. Прошедшие даты должны быть неактивны. При выборе диапазона дат Система должна автоматически рассчитывать и отображать общее количество ночей.
  7.  **Выбор услуг/штрафов:** Список доступных позиций, релевантных выбранной категории. Для каждой позиции должна отображаться цена. Для исчисляемых позиций (countable/duration) должна быть возможность указать количество с помощью кнопок "+/-".
  8.  **Выбор способа оплаты:** Список доступных методов: "СБП", "Банковская карта", "Наличные".
  9.  **Подтверждение:** Финальный экран со сводной информацией: ФИО гостя, номер, даты, перечень всех услуг/штрафов с ценами и количеством, итоговая сумма.
  10. **Проведение платежа:**
      - Для СБП: отображение QR-кода для оплаты и таймера ожидания.
      - Для Карты/Наличных: отображение инструкций для пользователя ("Приложите карту", "Внесите купюры") и таймера ожидания.
      - Система должна в реальном времени ожидать ответа от Бэкенда о статусе платежа через WebSocket.
  11. **Результат:** Краткое сообщение об успехе или ошибке операции с автоматическим возвратом на экран блокировки через 10 секунд.

##### 2.1.3. Модуль администрирования
- **FR-7 (Общие принципы):** Все разделы администрирования должны быть выполнены в едином стиле `CupertinoListSection` с навигацией "вглубь". Каждый раздел должен позволять управлять определенным аспектом Системы.
- **FR-8 (Управление оборудованием):**
    - **Эквайринг:** Проверка статуса соединения с терминалом; запуск тестового платежа на 1 рубль; запуск операции возврата; отмена текущей операции; вызов сервисного меню терминала.
    - **Купюроприемник:** Отображение текущего количества принятых купюр и процента заполненности. Установка максимального лимита купюр. Функция "Инкассация" для сброса счетчика. Режим тестирования для приема определенной суммы.
    - **Диспенсер купюр:** Отображение количества купюр в каждом из двух боксов. Функция пополнения боксов с указанием добавленного количества. Настройка номинала для каждого бокса (100, 500, 1000 и т.д.). Функция "Инкассация". Функция тестовой выдачи по одной купюре из каждого бокса.
- **FR-9 (Управление контентом и ценами):**
    - **Заставка:** Включение/выключение. Настройка времени бездействия до активации (в секундах). CRUD-интерфейс для изображений слайд-шоу: загрузка новых, удаление старых, изменение порядка перетаскиванием (drag-and-drop).
    - **Услуги и Штрафы:** Полноценные CRUD-интерфейсы для управления списком услуг и штрафов. Для каждой позиции должны настраиваться: название, цена, ставка налога (НДС), тип (исчисляемый, с длительностью).
    - **Цены на проживание:** Реализация механизма экспорта текущей ценовой сетки в CSV-файл и импорта для массового обновления цен из CSV-файла. Должна быть функция предпросмотра загружаемого файла.
- **FR-10 (Управление системой и отчетами):**
    - **Смены:** Отображение статуса текущей фискальной смены (открыта/закрыта, номер, время открытия). Кнопки для ручного принудительного открытия/закрытия смены.
    - **Безопасность:** Интерфейс для смены пароля текущего администратора (требуется ввод старого и нового паролей).
    - **Уведомления:** Интерфейс для ввода токена Telegram-бота и ID чата для отправки системных оповещений.
- **FR-11 (Отчетность):**
    - **Транзакции:** Просмотр полного списка исторических транзакций с возможностью детализации каждой. В детальном просмотре должна быть кнопка для ручной отправки/повторной отправки данных в 1С. Должна быть реализована функция экспорта всех транзакций в ZIP-архив.
    - **Метрики:** Просмотр базовых метрик работы терминала.

#### 2.2. Нефункциональные требования (Non-Functional Requirements)
- **NFR-1 (Производительность):** Отклик интерфейса на действия пользователя не должен превышать 200 мс. Анимации должны быть плавными (60 FPS).
- **NFR-2 (Надежность):** Система должна предусматривать механизмы обработки ошибок API (отсутствие сети, ошибки сервера) и сообщать о них пользователю в понятной форме. Приложение должно быть спроектировано для непрерывной работы 24/7.
- **NFR-3 (Безопасность):** Пароли и токены не должны храниться в открытом виде. Взаимодействие с Бэкендом должно осуществляться по защищенному протоколу HTTPS/WSS.
- **NFR-4 (UI/UX):** Дизайн должен строго соответствовать гайдлайнам **Cupertino (iOS)**. Все элементы управления должны быть крупными, с достаточными отступами для комфортного использования на сенсорных экранах. Язык интерфейса — исключительно **русский**.

#### 2.3. Требования к технологическому стеку
- **Фреймворк:** Flutter (последняя стабильная версия).
- **Архитектура:** Строгое следование принципам Clean Architecture с четким разделением на слои Presentation, Domain, Data.
- **Управление состоянием:** BLoC / Cubit.

### 3. Принципы взаимодействия с Бэкендом

Система является клиент-серверным приложением и не хранит бизнес-данные локально (за исключением сессионных токенов и кэша настроек).

- **3.1 (Протоколы):** Взаимодействие должно осуществляться по протоколу HTTP(S) для REST-запросов и по WSS для соединений реального времени.
- **3.2 (Формат данных):** Основной формат обмена данными — JSON.
- **3.3 (Аутентификация):** Для доступа к административным методам API должна использоваться сессионная аутентификация (например, на базе cookies).
- **3.4 (Типы запросов):** Система должна уметь запрашивать справочные данные (настройки, списки услуг, комнат), отправлять данные для создания/изменения сущностей (бронирования, транзакции) и получать асинхронные события о статусах операций через WebSocket.
- **3.5 (Отказоустойчивость):** Клиент должен корректно обрабатывать временную недоступность Бэкенда, отображая соответствующие уведомления и предоставляя возможность повторить операцию.
